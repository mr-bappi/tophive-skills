# Web & UI Design

**One relevant brief → the right artifact → build → inspect → repair → deliver.** This portable skill is a workflow and design-quality contract, not a file-access, image-generation, Figma, WordPress or deployment integration. Never claim tools or source access unavailable in the active client.

## 1. Route intent before design

Read `references/INTENT-ROUTER.md` for ambiguous requests. The user's explicit requested deliverable controls the mode:

| User asks | Mode | Expected completion |
|---|---|---|
| "Build/create/design me a landing page", "make a dashboard", "implement" | **BUILD** | Build a working requested artifact **this turn**, not just ideas, when authorized tools are available |
| "Show options", "explore concepts", "compare directions" | **EXPLORE** | 2–3 genuinely distinct art directions; no premature code |
| "Review/audit this screenshot/site" | **REVIEW** | Findings grounded in actual material; fix only if requested |
| "Polish/fix/align existing design" | **REFINE** | Preserve approved direction and scoped source; verify the change |
| Explicit Gutenberg content, SEO title/metadata or product description | **CONTENT/SEO HANDOFF** | Do not hijack into visual website work |

A product URL or screenshot is a **source/reference**, not permission to modify that page. Specific product names belong in project context and regression tests, **never** in the reusable skill's hard-coded behavior.

## 2. Pick domain and available evidence

**Website / marketing:** For short, underspecified BUILD requests load `references/SHORT-PROMPT-INTELLIGENCE.md` **before** choosing visual direction; recover trusted product context, tag assumptions and decide whether a single essential identity question is needed. Then load `references/STACK-ROUTER.md` and `references/MODERN-CSS.md` to select a proportional, compatible frontend stack. Start with `references/COMPOSITION-ENGINE.md` and `references/ART-DIRECTION-LIBRARY.md`; inspect `references/COMPOSITION-ATLAS.html` as schematic topology studies, not as a template. For relevant product interactions load `references/PRODUCT-EXPERIENCE-ENGINE.md`; after rendering perform `references/VISUAL-CRITIC-LOOP.md`. Then load `references/WEBSITE-WORKFLOW.md`, `references/CREATIVE-DIRECTION.md` and `references/CREATIVE-DIVERSITY.md` for new builds. On new creative work, run `references/DISTINCTIVENESS-GATE.md` before final handoff. Load `references/TYPOGRAPHY-INTELLIGENCE.md` for type selection and `references/MOTION-INTELLIGENCE.md` for an **adaptive motion decision** before implementation. The AI chooses STATIC, QUIET, EXPRESSIVE or IMMERSIVE from the product, content and art direction; **animation is never mandatory**, and zero motion may be the strongest deliberate choice. No scroll reveal, parallax, GSAP or animation quota. When motion is selected, implement it and verify its observable behavior; when stillness is selected, preserve that direction. Use `references/MOTION-QUALITY-GATES.md` to verify the decision and any implemented motion. Load `references/DESIGN-PRINCIPLES.md` when useful.

**Dashboard / application / WordPress admin:** Load `references/DASHBOARD-WORKFLOW.md`, `references/APPLICATION-CRAFT-GATE.md`, `references/APPLICATION-VISUAL-CRAFT.md`, `references/STACK-ROUTER.md` and `references/DASHBOARD-COMPONENTS.md` first. **Operational usability is the floor, not visual excellence:** for greenfield branded applications evaluate materially different workspace compositions, develop a cohesive component identity and inspect real rendered screens using the application visual-craft veto. Do not equate minimal/quiet with bland or generic, and do not mandate any trend, motion or component library. For wide/large/sortable data-heavy tables also load `references/DATA-GRID-ENGINE.md`; for React/Next.js work load `references/REACT-ARCHITECTURE.md`; for CSS composition load `references/MODERN-CSS.md`; for genuinely greenfield branded application UI, selectively use `references/CREATIVE-DIVERSITY.md` without imposing marketing aesthetics; load `references/TYPOGRAPHY-INTELLIGENCE.md` and `references/MOTION-INTELLIGENCE.md` selectively for typography and operational feedback; for existing UI or focused critique also load `references/UI-REVIEW.md`. Never apply marketing hero sizes, promo cards or large landing whitespace to operational software.

**Advanced motion / 3D / video (selectively):** Load `references/GSAP-LENIS.md` for justified scroll timelines, `references/THREE-R3F.md` for actual interactive 3D, and `references/VIDEO-MOTION.md` for media, compositing or export; combine only when task scope requires it. These are engineering guides, not a license to add dependencies by default. Verify APIs with installed versions and provider docs. Preserve native fallbacks, performance budgets and lifecycle cleanup. An interactive video editor is a separate application build, never implied by video decoration.

**All BUILD/REFINE:** Do not claim superiority over a normal no-skill model until the external blinded A/B benchmark has independent evidence. Local package tests do not measure creative merit. Load `references/ONE-SHOT-EXECUTION.md`, `references/IMPLEMENTATION-CONTRACT.md`, `references/QUALITY-GATES.md` and `references/UX-RELIABILITY-REGRESSIONS.md`. For every critical UI control, define a scroll owner, route/reload state, selection/overlay behavior and a browser acceptance invariant before claiming premium completion. Load `references/VISUAL-ASSETS.md` when the task involves visual evidence, images, logos or illustrations. Load only files applicable to the selected route.

**Mandatory modular CSS for frontend BUILD/REFINE:** When authoring or changing custom CSS, also load `references/MODULAR-CSS-ARCHITECTURE.md` and enforce it from the first build: owner-scoped source modules, centralized tokens, a reproducible CSS build/check or native framework import graph, no giant handwritten global stylesheet, and real responsive/visual regression. For an existing application, preserve the approved style stack and refactor only the authorized area; do not impose a folder template or replace an established modular setup. A single **generated** runtime CSS bundle is valid; a single **editable source monolith** is not.

**Prompt provenance for all authorized BUILD/REFINE work:** Load references/PROMPT-PROVENANCE.md and preserve a source-of-truth prompt chain where writable: exact creator-supplied original (immutable), selected design decisions, approved revisions, and a reconstructed final recreation brief grounded in verified code/screenshots. Never invent creator wording if original is unknown or inaccessible. An assistant-invented initial challenge is not the user's exact original. The bundled scripts/prompt-lineage.py can capture, record and verify artifacts; it never scrapes chat history or generates designs. In public metadata a final recreation prompt stays marked reconstructed even when the separate original is available.

Read the target repository's `AGENTS.md`, approved decisions, actual code, product docs, assets and screenshots **if and only if accessible**. Product facts, local app contracts and user-approved direction outrank design teaching examples. The optional master library is `~/Documents/design-lab/` only with authorized filesystem access; never treat its files as present in a cloud environment.

## 3. Execute rather than pause unnecessarily

For explicit **BUILD**, infer safe creative defaults from reliable context, choose the strongest design direction internally, and complete the actual requested artifact within the available workflow. When a prompt names a project but its actual product/category cannot be established from accessible approved context, do **not** invent its purpose: follow `references/SHORT-PROMPT-INTELLIGENCE.md` and ask one essential question only if a correct product-specific build depends on the answer. Do **not** require three direction approvals first. For explicit **EXPLORE**, show distinct concepts and await selection when necessary. If input is incomplete, mark unknown claims `TBD` or proposed and use clearly illustrative UI data; ask only when a missing requirement blocks a valid deliverable or permission.

Website: treat the first plausible design as a **hypothesis, not a winner**. Extract the visitor's task and authentic proof; develop three materially different internal creative candidates; reject decorative, interchangeable, unsupported or mobile-infeasible directions; then select the best tradeoff for comprehension, product-specific identity, visual craft and feasibility before styling. Use the **creative selection + render challenger** in `references/COMPOSITION-ENGINE.md` and `references/VISUAL-CRITIC-LOOP.md`. Do not require a particular aesthetic, color, headline pairing, amount of motion or arbitrary revision count. Derive the grid, reading path, hero logic, typography and section topology from product evidence, not recurring brand-stereotype patterns. Require a real experience or truthful proof mechanism; avoid filler cards and end-of-page CTAs by habit. Also require an authentic promise, product-derived (not reused-by-default) visual system, genuine product demonstration, useful navigation and real CTA. Dashboard: real user job, information hierarchy, suitable density, forms/tables/filters and observable interface states; **plus a distinct, deeply crafted visual/interaction system verified across multiple active application states**. No fake customer numbers, certification, unsupported features or backend behavior.

For new brands, check that unrelated prior work has not become an accidental template. Sharing an approved brand/design system is valid and must be preserved. Novelty must not override product truth, usability, or locked user decisions.

Never silently overwrite approved source, discard pre-existing changes, commit, push, deploy, perform destructive actions or change an installed client. Use isolated prototypes when integration is not authorized. A working prototype is not a production integration.

## 4. Inspect, repair, finish

On new website builds, perform pre-render creative veto, inspect initial render, make any structural repair indicated by evidence, and retest. For all BUILD/REFINE work, apply the applicable U01–U15 regression gates in `references/UX-RELIABILITY-REGRESSIONS.md` within the same user request: inspect hard reload, actual scrolled/hover/focus/empty/filled states, scroll ownership and overlay transitions; preserve the existing UI while repairing causes. One-shot delivery means internal iterations BEFORE the user's review, not unverified first-render perfection. A prettier gradient or swapped font is not a structural repair. Use `scripts/visual-critic.py` when an auditable screenshot/repair record is useful; a completed record is NOT an independent creative-quality score. When browser/runtime tools exist, review rendered output and behavior at practical mobile/tablet/desktop sizes (prefer 360, 390, 768, 1024, 1440, 1920). Test overflow, actual typography, contrast, keyboard/focus, functionality, errors, reduced motion and layout rhythm; fix failures and retest. On scoped edits rerun affected regressions. See `references/QUALITY-GATES.md` and `references/MOTION-QUALITY-GATES.md`. Motion must be observed, not inferred from a stylesheet. An inaccessible browser or missing external credentials means **NOT TESTED**, never implied PASS.

For advanced applications record component interaction/state matrices, large-grid representative fixture sizes, 3D fallback states, video playback/export evidence and motion start/mid/end/reduced-motion recordings where relevant. Reference documentation and static tests cannot prove functional runtime behavior or blinded creative quality.

When Node + Puppeteer + Chrome are actually available for a **local** page, use bundled `scripts/visual-smoke.cjs --url <local URL> --out <local screenshots directory>` for viewport screenshots, image/overflow/runtime error evidence; the user agent must still review visual craft and accessibility manually. The script cannot self-grant tool access or deploy.

Before final handoff, when project files are accessible, update the final recreation brief from accepted implementation and meaningful QA; verify its prompt provenance digests. Do not treat final prompt text as a guarantee of pixel-perfect recreation. Preserve source assets/screenshots separately for reliable rebuilding.

Final response: link or path to real artifact, what was created, proof of checks with PASS/FAIL/NOT TESTED, remaining limitations, and whether production was untouched. Never substitute a pitch, checklist or mockup screenshot when runnable source was requested. No design skill can guarantee a perfect result from every prompt.
