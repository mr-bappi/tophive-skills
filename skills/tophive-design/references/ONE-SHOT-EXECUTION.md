# One-shot execution contract — build, don't stall

One-shot refers to **one user request**, not an assurance of error-free production code. Carry out the full authorized task without requiring unnecessary intermediate approvals.

## Plan inside the work

1. Discover: goal, audience/operator, primary task, evidence source, target stack, authorized destination, constraints, existing accepted design. For underspecified products run `SHORT-PROMPT-INTELLIGENCE.md`: source-tag the five-slot internal brief; distinguish a category-known reversible concept from an unresolved project identity.
2. Choose: select a distinct, purposeful visual direction; note why it fits. Do not spend the response proposing three directions when BUILD was requested.
3. Architect: define page/story or application navigation/data/workflow; specify assets and working interaction states. Write the screen risk contract from `UX-RELIABILITY-REGRESSIONS.md` for critical routes (scroll owner, shell state, selection type, dataset scale, reload and empty/filled transitions).
4. Implement: produce actual usable files/components with semantic structure, responsive styling and connected front-end interactions. Follow target stack rather than replacing it with a favored framework.
5. Inspect: when tooling exists, start safe local preview and capture wide/mobile; check interactions, console/runtime errors, overflow, accessibility, content, spacing and assets.
6. Repair: fix *root cause*, not endless cascading CSS overrides; repeat checks on modified breakpoints. Preserve user-approved sections.
7. Handoff: identify source/preview, what genuinely works, QA evidence and NOT TESTED items. Production untouched unless explicitly approved.

## Stop conditions / permission

No silent commit/push/deploy, account installs, plugins, schema/data migrations, external posting, purchasing or destruction. If a tool is unavailable or blocked, say so and deliver the best honest partial artifact. Do not claim pending implementation was completed, or promise asynchronous work.

## Avoid common traps

- A large heading and three generic cards are not a complete distinctive landing page.
- A marketing shell with decorative charts is not an operational dashboard.
- Source compile success without browser verification is not visual QA PASS.
- Placeholders must be labeled demo-only and must not masquerade as true product statistics.
- A screenshot is not a functional source implementation.
- Don't convert requested marketing visuals into WordPress SEO snippets unless explicitly asked.
- Preserve existing repository state, design tokens and approved composition. A new user request updates only the named dimension of a prior locked brief.
