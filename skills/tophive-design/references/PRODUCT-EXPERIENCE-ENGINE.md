# Product Experience Engine — prove by doing

A distinctive site is not a pretty sales wrapper. It helps visitors understand or *perform* the product's core job. For greenfield marketing, include a credible interactive proof if that can be built with available front-end data; otherwise present a labelled static explanation rather than simulated functionality.

## 1 — Identify the authentic job

Record: actor, trigger, object, decision, action, observable outcome, permission boundary. The signature experience must relate to this chain. Industry-themed decoration without an observable product mechanism does not count.

Examples of shapes, NOT mandatory brand-specific templates:
- Security investigation: select a signal, follow an evidence chain, inspect impact and acknowledge a next action. Never imply access to a real security backend.
- Science exploration: change one variable, observe a visual result, read a short explanation and reset. Distinguish a simplified demonstration from a real scientific simulation.
- Literary reading: browse by genre, change comfortable reading preferences, save locally within the live page when clearly described as local state; focus on content, not random animations.
- Furniture: inspect scale, material, finishes and dimensions with honest available assets, never imply true AR/checkout if unavailable.
- Operator/dashboard: filter/sort/inspect items, change authorized demo statuses, show empty/loading/error states and consequences.

## 2 — Define the interaction contract BEFORE decorative CSS

| Required | Question |
|----------|----------|
| Entry | How does the visitor start without an explanation? |
| Input | What control or content choice is meaningful? |
| State | What changes in a visible, understandable way? |
| Feedback | What confirms the consequence? |
| Recovery | Can the user reverse/reset the action? |
| Accessibility | Keyboard, labels, focus, hit targets, reduced motion and static fallback? |
| Truth | Is the demo honest about synthetic data, unavailable integrations and persistence? |

A tab that changes an illustration without explaining a user outcome may be decoration. A live calculator with fictional verified metrics is actively misleading.

## 3 — Experience-first page architecture

Give the signature experience prime real estate only if it teaches the visitor more than a paragraph would. The demo may be the hero, the second scene, the article navigator or a pinned inspector. Other sections must be justified by the visitor's next question, not by an obligatory template checklist.

Do not insist that every product needs tabs, a simulation, shopping UI or an animated canvas. For contemplative publications, distinctive navigation and excellent reading modes may outperform a gadget.

## 4 — Verification with observable states

At least one meaningful transition should be exercised and documented: initial, action, resulting UI, reverse/recovery and keyboard behavior; note what is only illustrative. When browser automation is unavailable mark behavior NOT TESTED and do not call it verified. If high-stakes functionality cannot be safely demonstrated, use a truthful explanatory model with limits.

An interaction does not count as validated merely because onclick/transition code exists. The page must produce visible understandable state and survive mobile/reduced motion.
